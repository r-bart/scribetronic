# Implementation Plan: agent-friendly CLI for v0.2.1

**Date**: 2026-05-04
**Status**: Draft

---

## Overview

Apply the Tier-1 fixes from the post-review audit ("Designing CLI for Agents") so that scribetronic's seven commands behave correctly when invoked by an agent rather than a human terminal user. Three independent vectors: machine-readable output (`--json`), stdout/stderr discipline, and TTY/`NO_COLOR`-aware chrome. All in v0.2.1, all local — **no push, no tag, no release**.

Plus two Tier-2 polish items that fit naturally in the same pass: granular exit codes (so `scribetronic doctor; echo $?` lets an agent distinguish state-error from misuse) and `--yes` for `style --reset` (the only command that hard-fails without a TTY).

## Requirements

- [ ] `scribetronic list --json` emits `{ "skills": [...] }` only on stdout. Exit 0.
- [ ] `scribetronic info <skill> --json` emits `{ name, frontmatter, body, path }` on stdout. Exit 0; exit 2 if skill not found (was 1).
- [ ] `scribetronic doctor [path] --json` emits `{ ok, checks: [{ label, ok, detail }] }`. Exit 0 if all pass, exit 3 if any fail (was 1).
- [ ] All decorative output (clack `intro/outro/note/spinner`, headers, summary boxes) routes to **stderr**, never stdout, in the seven commands.
- [ ] When `process.stdout.isTTY === false` OR `process.env.NO_COLOR` is set, clack chrome is suppressed and replaced with plain `console.error` lines.
- [ ] Exit codes follow the new contract: `0` success, `1` unexpected, `2` usage error (bad args/path), `3` state error (config drift, missing plugin registration, doctor failure).
- [ ] `scribetronic style --reset` accepts `--yes` (or `SCRIBETRONIC_YES=1` env) to bypass the confirm prompt; non-TTY without `--yes` still exits with the original error.
- [ ] All 78 existing tests still pass.
- [ ] New tests cover: `--json` shape per command, stdout/stderr separation, NO_COLOR/non-TTY behavior, granular exit codes, `--yes` flag.
- [ ] `docs/cli-reference.md` documents `--json`, the exit-code table, and `--yes`.
- [ ] `CHANGELOG.md [0.2.1]` adds an "Agent-friendly CLI" section.

---

## Approach Analysis

### Option A: per-command `--json` flag, ad-hoc

Add `.option('--json', '...')` to each command in `index.ts`, branch inside each command function on `if (options.json) { ... } else { ... }`. Stderr/stdout routing is also per-command.

**Pros**: Local. Easy to test. No abstraction overhead. Matches devtronic's pattern.
**Cons**: 7 places to keep in sync. If we add a new command, easy to forget. No central place for env-var handling.
**Complexity**: Low.

### Option B: shared `output` module + global flags

Build `src/utils/output.ts` exposing `out.data(payload)`, `out.note(msg)`, `out.success(msg)`, `out.error(msg)`. The module reads global flags (`--json`, `--quiet`) once and routes accordingly. Each command imports the module and never touches `console` or `clack` directly.

**Pros**: Single source of truth. New commands inherit correct behavior. Easy to audit. Future-proof for `--quiet`, `--cwd`, `--format yaml`, etc.
**Cons**: More upfront refactor. Touches all 7 commands. Higher test churn.
**Complexity**: Medium.

### Recommendation

**Option B.** The cost is real (~3h refactor) but the benefit compounds with every future command, and the audit's whole point is that agent-friendliness is a *posture*, not a feature. Per-command branches in Option A degrade fast — within 2-3 PRs we'd have inconsistent JSON shapes and accidentally-stdout warnings. The shared module keeps the discipline mechanical.

Trade-off accepted: Option B is more code today, less drift over time.

## Implementation Phases

### Phase 1: Shared infrastructure

#### Task 1.1: Create `output.ts`
**File**: `packages/cli/src/utils/output.ts`
```typescript
import chalk from 'chalk';

interface OutputConfig {
  json: boolean;
  isTTY: boolean;
  noColor: boolean;
}

let cfg: OutputConfig = {
  json: false,
  isTTY: Boolean(process.stdout.isTTY),
  noColor: Boolean(process.env.NO_COLOR),
};

export function configure(opts: Partial<OutputConfig>): void {
  cfg = { ...cfg, ...opts };
  if (cfg.noColor || !cfg.isTTY) {
    chalk.level = 0;
  }
}

/** Machine-readable payload — stdout. The ONLY thing that goes to stdout. */
export function data(payload: unknown): void {
  if (cfg.json) {
    process.stdout.write(JSON.stringify(payload) + '\n');
  } else {
    // Non-JSON callers pass either a string (printed verbatim) or the same
    // payload object that the JSON path uses; the command-specific human
    // formatter is invoked separately via `humanize` callback.
    if (typeof payload === 'string') {
      process.stdout.write(payload + '\n');
    } else {
      // Each command must register a humanizer — see commands/list.ts etc.
      throw new Error('output.data() called with non-string in non-JSON mode without humanizer');
    }
  }
}

/** Decoration / progress / hints — stderr, suppressed in JSON mode. */
export function note(msg: string): void {
  if (cfg.json || !cfg.isTTY) return;
  process.stderr.write(msg + '\n');
}

/** Success message — stderr in human mode, suppressed in JSON mode. */
export function success(msg: string): void {
  if (cfg.json) return;
  process.stderr.write((cfg.isTTY ? chalk.green('✓ ') : '') + msg + '\n');
}

/** Warning — stderr always; in JSON mode emitted as a structured event. */
export function warn(msg: string): void {
  if (cfg.json) return;
  process.stderr.write((cfg.isTTY ? chalk.yellow('! ') : 'WARN: ') + msg + '\n');
}

/** Error — stderr always. JSON mode emits a structured envelope on stdout instead. */
export function error(msg: string, code?: string): void {
  if (cfg.json) {
    process.stdout.write(JSON.stringify({ ok: false, error: { message: msg, code } }) + '\n');
  } else {
    process.stderr.write((cfg.isTTY ? chalk.red('error: ') : 'error: ') + msg + '\n');
  }
}

export function isJson(): boolean {
  return cfg.json;
}
```

## Risk Analysis

### Edge Cases

- [ ] `list` when zero skills: JSON returns `{skills: []}`, exit 0 (currently exits 0 with a warning to stdout — needs to move to stderr).
- [ ] `info` when frontmatter has nested objects (e.g. legacy `sources: {references: [...]}`): JSON serialization must preserve nesting; the parser already returns flat strings/arrays, so this is moot post-frontmatter-normalization, but assert in tests.
- [ ] `doctor` when `.claude/settings.json` is malformed JSON: `readClaudeSettings` returns `{}` (already covered by `settings.test.ts`); doctor reports the plugin as not-registered. Confirm exit 3 still fires.
- [ ] `style --reset --yes` when seed is missing: still must exit `Unexpected` (1) — that's a real failure, not a usage one.
- [ ] `init` with pre-existing `.claude/settings.json` containing a different marketplace: the merge is idempotent; assert no stdout pollution in JSON path (none — init doesn't have JSON, mutates only).

### Technical Risks

- [ ] **Tests that spy on `console.log` will break en masse.** Mitigation: do Phase 5 immediately alongside Phases 3-4, not at the end; CI matrix will catch regressions.
- [ ] **`@clack/prompts` writes directly to `process.stdout` regardless of our wrappers.** Mitigation: wrap clack calls with `if (!cfg.isTTY || cfg.json) return earlyAlternative(...)`. Verified in audit — clack does write to stdout.
- [ ] **chalk auto-detection vs forced level**. Setting `chalk.level = 0` is a global mutation; safe in CLI process but a footgun if `output.configure` is ever called twice. Add idempotency check.
- [ ] **JSON-mode error envelope on stdout violates "stderr for errors"**. This is intentional per the audit (agents pipe stdout to a JSON parser; surfacing structured errors there is the convention — see `gh --json`, `kubectl --json`). Document this explicitly in cli-reference.

## Testing Strategy

- **Unit**: `output.ts` (Task 5.1) — 8-10 cases covering all modes
- **E2E (spawn-based)**: `json-mode.test.ts` (Task 5.2) — 6-8 cases asserting stdout/stderr/exit per command in `--json` mode with `NO_COLOR=1`
- **Existing tests adjusted**: 7 files, ~20-25 assertions migrated from stdout to stderr
- **Manual verification**:
  ```bash
  # human mode
  scribetronic doctor /tmp/foo
  scribetronic list

  # agent mode
  scribetronic doctor /tmp/foo --json | jq '.ok'
  scribetronic list --json | jq '.skills | length'
  scribetronic info agenda --json | jq '.frontmatter'

  # non-TTY behavior
  scribetronic doctor /tmp/foo > /tmp/out 2> /tmp/err
  cat /tmp/out  # empty in human mode (chrome went to stderr)
  cat /tmp/err  # the report

  # NO_COLOR
  NO_COLOR=1 scribetronic list  # no colors anywhere

  # --yes
  scribetronic style --reset --yes  # works without TTY
  SCRIBETRONIC_YES=1 scribetronic style --reset  # also works
  ```
